# GilgameshBot — notes for Claude Code

Dalamud (FFXIV) plugin that relays Free Company chat to Discord. Read `README.md` for what the plugin does and how it is set up before changing behaviour.

## Stack

- C# / .NET 10, `Dalamud.NET.Sdk/15.0.0` (Dalamud API 15, game patch 7.5+). The SDK sets the target framework (`net10.0-windows`), x64, unsafe blocks and the Dalamud references; do not add them to the csproj by hand.
- Discord.Net 3.20.1 (`Discord.Net.WebSocket`) for the gateway + REST; `Discord.Net.Webhook` posts The Fat Cat Weekly through a channel webhook.
- SixLabors.ImageSharp 3.1 + ImageSharp.Drawing 2.1 (fully managed) draw the calendar image and the weekly header; fonts are embedded resources (OFL, `Calendar/Fonts`), the weekly's pictures too (`Weekly/Assets`).
- Dalamud reference assemblies come from `%AppData%\XIVLauncher\addon\Hooks\dev\` or `DALAMUD_HOME`.

## Build / run

```powershell
dotnet build GilgameshBot/GilgameshBot.csproj -c Release
```

For development, load as a dev plugin (`/xlsettings` → Experimental → Dev Plugin Locations). Logs: `/xllog` in game, or `%AppData%\XIVLauncher\dalamud.log`.

Users do not build: they add the custom plugin repository `https://github.com/Marco-Andre90/gilgameshbot-ffxiv/releases/latest/download/repo.json` in `/xlsettings` → Experimental → Custom Plugin Repositories and install from `/xlplugins`. `repo.json` is generated by `.github/workflows/release.yml` and uploaded as a release asset (never committed — `release` is protected).

## How it works

- **Branches.** N Free Company branches, one per (home world, FC name), each with its own Discord server, relay channel and state channel. The branch is resolved from the logged-in character, so a member with characters in several branches configures nothing extra.
- **Presence queue.** Several members may run the plugin at once. Each instance keeps its own presence message, tagged with its branch's relay channel id, in the state channel (shared by every branch on the server, never the relay channel itself) and edits it every heartbeat; the oldest alive message is the leader and the only instance that relays. A leader also holds a lease — it stops relaying once its own heartbeat is older than the stale window — so a takeover can never duplicate messages. Followers drop what they receive.
- **Setup code.** A `GB2:` string (base64url JSON) carrying the token and every branch, handed over by Discord DM (`/gilga send`, `/setupcode`; receipt on import, timed expiry) or the clipboard, so one member configures all the others.
- **Shared configuration.** The branch table and the presence timers, with a revision, live as one bot-authored message (marker + `gilgamesh-config.json`, **no token**) in every distinct state channel, found among the newest 100 messages (not pinned). "Publish to Discord" (Advanced tab, confirmed) writes revision `max(local, remote) + 1` to all of them; it is refused on an incomplete branch, on any branch whose server / relay / state / roster channel does not resolve with the live client, without *Attach Files* in a state channel, and when any channel already holds a newer revision. Every plugin reads all state channels once per session, on Ready (the configuration rarely changes; no polling), and applies a newer revision on the framework thread (branches + timers replaced; personal toggles kept), then reconnects if its active branch disappeared or its IDs or tag changed. Setup codes carry the revision as optional `rev`; an import sets it (0 when absent) so the next sync heals an old code.
- **Slash commands.** `/setupcode` (DMs the invoker a setup code, same delivery as `/gilga send`), `/relaystatus` (who is relaying, how many on standby), `/fcscan` and `/calendar`. Registered per branch guild on Ready, after the channel resolution, one `CreateApplicationCommandAsync` per command that is missing or differs (name + description compared; a create under an existing name updates it in place, keeping its id) — never a bulk overwrite, because the owner's per-role grants hang off the command ids and an older plugin must not delete a newer one's commands (plugins from before the calendar still bulk-overwrite their three commands, deleting `/calendar` until a current plugin reconnects and recreates it with a new id — which resets the owner's per-role grants on `/calendar`; the Calendar tab's controls do not depend on it). Changing a command's options means changing its description too. Every connected instance receives every interaction; only the leader of the branch whose `GuildId` matches answers — except `/calendar` (and its autocomplete), which any connected plugin answers, first to acknowledge wins. Who may run the commands is decided by Discord's command permissions alone (registered as Manage Server; the owner opens them to roles under Integrations). A code fetched with `/setupcode` lives 5 minutes unimported, one sent with `/gilga send` 24 hours.
- **FC roster.** A manual scan (settings tab or `/fcscan <world>`, any connected instance) reads the FC's Lodestone member pages, diffs them against the previous scan and reports joined / left / renamed / time in the configured starter rank in the roster channel: one report per FC (found by its title, edited in place or reposted when its part count changes, older copies deleted) plus a "Roster updated" notice that replaces the previous one. State lives in Discord, not in the config: one bot-authored state message in the roster channel (first message, or pinned when the channel was not empty) carrying one `roster-<lodestoneId>.json` per FC, keyed by Lodestone character id. `/fcscan` is registered identically in every guild; the FCs come from autocomplete (shown as "FC @ World", sent as the Lodestone ID), never from registered choices, so differing configs never re-register.
- **FC calendar.** One calendar for the whole FC: a global calendar channel and a list of Apollo channels on its guild (`Configuration.CalendarChannelId` / `ApolloChannelIds`, optional top-level `calendarChannel` / `apolloChannels` in the setup code and the shared configuration; a setup code without them leaves the local ones alone). It is kept by the plugins connected to the calendar channel's guild. The source is Apollo's event posts (author `475744554910351370`, a `Time` field with `<t:…>` start/end, the event id from the `manage:<id>` button), read over REST: the **Message Content** intent is switched on in the Developer Portal but deliberately **not** requested on the gateway (only `Guilds`), so plugins never receive the server's message stream. The calendar channel may be a thread (permissions come from its parent). Discord only sends active threads on connect, so channels are resolved through `CalendarChannels.ResolveAsync` — the gateway cache, else REST — and an archived thread is reopened before writing. The service keeps the guild id, not the `SocketGuild`, so a re-Ready never leaves it with stale state; before editing it re-reads the message and rebases a settings change on whatever another plugin wrote meanwhile. The calendar message (bot-authored, recognised by its `gbcal:` custom ids; first message, or pinned when the channel was not empty) carries the image (PNG for Clean, JPEG for the grainy themes) above an embed — Discord shows attachments before embeds — with the calendar's name as title, the upcoming events with Discord timestamps, and controls. The image has no times: events are placed on days in the calendar's zone (US Central by default; Sunday-first for the Americas). Every connected plugin on the guild runs an hourly loop (not only leaders: the leader may be on a version without the calendar) and skips a message the bot edited < 55 min ago; renders are seeded by month + theme (a stable number, never `GetHashCode`), so concurrent writers write the same picture, and stray copies are deleted on every pass. A shared configuration file without `"calendar": true` comes from a plugin that predates the calendar: applying it keeps the local calendar settings; with it, its calendar settings (none included) replace the local ones. Settings live on the calendar message: theme and zone in its components' custom ids, the name as its embed title (`📅 ` + name); `/calendar name|theme|timezone` and the Calendar tab's *What everyone sees* controls rewrite them (the tab works even while an older plugin has deleted `/calendar`), `/calendar refresh` and *Update now* redraw. Clicks and `/calendar` are answered by any connected plugin of that guild (first to acknowledge; 40060 swallowed): on the channel message with a new ephemeral reply (`DeferLoadingAsync(ephemeral)` + `ModifyOriginalResponseAsync`), on an ephemeral reply by updating it in place (`DeferAsync` + `ModifyOriginalResponseAsync`); months browse one each way.
- **The Fat Cat Weekly.** One weekly for the whole FC: an announcement channel, an approval channel and an approver role (`Configuration.WeeklyChannelId` / `WeeklyApprovalChannelId` / `WeeklyApproverRoleId`; optional `weeklyChannel` / `weeklyApproval` / `weeklyRole` in the setup code and the shared configuration, the latter flagged `"weekly": true` like the calendar). `WeeklyDraftMode` is personal. It is kept by the plugins connected to its server; both channels are text channels (no threads) on one server with the Apollo channels. `/weekly [draft]` answers with the form straight away (no defer: a modal must be the first response); *Start weekly* on the tab posts a "Write the weekly" button in the approval channel, whose click opens the form (custom id `gbweekly:modal:<draft>:<fill message id>`, deleted once previewed). A submit posts the preview in the approval channel — the exact message, files included — mentioning the role through an allow-list of that one id (none in draft mode), with Approve / Reject (draft: Delete draft, for its author or the role). Approvers are checked through the interaction member's `RoleIds`. Approve removes the buttons first, then skips the post if the announcement channel has a weekly newer than the preview, then rebuilds the message from the preview's embeds (re-reading Apollo, re-rendering the header) and sends it through the bot's webhook (created on first use with the icon; name and avatar put back if removed; username sent on every post). No state lives in the plugins: the issue number and the week are in the posted weekly's footer (`The Fat Cat Weekly · Issue No. N · Next issue: Mmm d, yyyy`), the issue number is the newest webhook message named The Fat Cat Weekly among the announcement channel's newest 100, + 1, and the week starts on the posting day in the calendar's time zone (`CalendarService.TimeZoneAsync`). The events embed lists Apollo events in [post, post + 7 days); every connected plugin on the server checks hourly and, while the week lasts, re-edits the newest weekly (only the bot's webhook's) with every file re-attached when the events text changed. The form's field limits keep the message under Discord's 6000 characters.
- **Distribution.** A custom plugin repository: `.github/workflows/release.yml` builds on merge into `release` and attaches the versioned zip, `latest.zip` and a generated `repo.json` to the GitHub Release; the repository URL is the `releases/latest/download/repo.json` redirect.

## Rules of the road

- **Scope discipline.** The repository documents and ships only what exists. Do not add speculative features, roadmap files or lists of limitations; discuss new features with the owner before starting.
- **Branch is chosen from the logged-in character** (home world + FC name), never from a manual selection. `IPlayerState.HomeWorld` + `InfoProxyFreeCompany.Instance()->NameString`, read on the framework thread; `IObjectTable.LocalPlayer.CompanyTag` is read too but the tag is only a label and a secondary check — FC tags are not unique within a world, FC names are. Both are empty for the first frames after login, so resolution retries for ~30 s and is cancelled on logout; a throwing native read must feed that retry loop, never end it. No matching branch ⇒ do not connect, and say why through `DiscordBridge.SetUnavailable`.
- **Game thread never blocks.** `IChatGui.ChatMessage` runs on the game's main thread: extract + enqueue only. All Discord I/O lives on background tasks in `DiscordBridge`.
- **Slash command and component handlers never block the gateway task:** acknowledge first (`DeferAsync` / `DeferLoadingAsync`), then do the work on a background task and answer ephemerally (`FollowupAsync` / `ModifyOriginalResponseAsync`). Swallow `HttpException` with `DiscordCode == InteractionHasAlreadyBeenAcknowledged` (40060): two branches may share one guild, so two leaders may both answer.
- **Never log or print the bot token.**
- **Setup code contains the token.** Only ever moves through the clipboard or the Discord DM it is sent in; never log, print or render it. Decode failures produce a fixed human message and never echo any part of the input.
- **Shared configuration never carries the token**, and its model (`SharedConfigFile`) has no token field. Only messages authored by the bot and starting with the marker count; a file is validated like a setup code (`SetupCode.TryValidateBranches`) and used whole or not at all. Publishing must pass the live preflight: one bad ID reaching every plugin would leave them unable to connect, and so unable to receive the fix.
- **Setup codes sent by DM carry a receipt pointer; the importer scrubs the DM after its first successful connect; the sender deletes unimported DMs after their lifetime (24 h for `/gilga send`, 5 min for `/setupcode`).** The pointer is optional in the payload — a clipboard code has none and the format version does not move.
- **Mentions are an allow-list.** Every send passes `AllowedMentions` with exactly the user/role IDs the resolver produced; never widen it to `AllowedMentionTypes.Users/Roles/Everyone`. `@everyone`/`@here` are also neutralised in the text — keep both layers.
- **Presence:** an instance only ever edits/deletes its own presence message; the only exception is deleting stale (>10 min) messages. Followers drop messages, never buffer them. Leader election is scoped per branch by the `[relayChannelId]` tag in the presence message, so any number of branches may share one state channel; the state channel must never be the relay channel (the queue is read from the newest 100 messages). The shared configuration message is the one other message allowed there, and the presence code leaves it out of its "not dedicated" count.
- **Roster scans never write from bad input.** A partial Lodestone list (non-200, redirect, count ≠ total), missing channel permissions or an unreadable state message aborts before anything is posted or saved — a partial list would report members as having left. The writes themselves are not transactional, on purpose: the report goes out before the state is saved, so a failed save only means the next scan reports the same changes again (in the same, edited report). Only the bot edits the state message; an edit re-uploads every FC's file. A roster channel is never any branch's relay or state channel (checked on save, on import and before every scan), because the scan edits and deletes the bot's messages there. Reports use `AllowedMentions.None` and escape names and rank names.
- **The calendar never writes from bad input.** An unreadable Apollo channel (missing, no *View Channel* / *Read Message History*) aborts the update and leaves the last calendar in place. An Apollo post without embeds (Message Content off) counts as unreadable. A calendar channel is never any branch's relay, state or roster channel nor an Apollo channel (checked on save, on import, on publish and before every update; a calendar that clashes on import is dropped, and a local one that clashes with imported branches is cleared), because the update edits and deletes the bot's marker messages there; a roster channel is likewise never a calendar channel. Calendar text uses `AllowedMentions.None`, escapes titles and neutralises mass mentions; only the bot's own calendar message is read for settings, and unknown theme/zone keys fall back to the defaults.
- **The weekly never posts twice and never writes from bad input.** Approve takes the buttons off before anything else and checks for a newer weekly before sending; an unreadable Apollo channel stops a preview, a post and a refresh. A failed preview hands the officer's text back as a file; a failed post puts Approve / Reject back with the reason. The weekly's channels are never any branch's relay, state or roster channel, the calendar channel nor an Apollo channel, and never the same channel (checked on save, on import, on publish and before every write; a weekly that clashes on import is dropped); calendar and roster channels are likewise never a weekly channel. Previews mention only the approver role (`AllowedMentions` with exactly its id); the posted weekly and every other weekly message use `AllowedMentions.None`; officers' text keeps its markdown but mass mentions are neutralised.
- **Rendering stays light.** One render at a time (the calendar and the weekly header share `CalendarRenderer.Gate` and its pool), a private ImageSharp memory pool released after each render, always off the game/draw thread. The hourly loop renders only when the calendar is due; clicks and `/calendar` are rendered by the one plugin that acknowledged first.
- **`Disconnect()` is fire-and-forget.** Only `Dispose()` waits (bounded) so the Offline notice gets out during unload.
- Namespace is `GilgameshBot.Relay`, not `GilgameshBot.Discord`, to avoid clashing with the `Discord` root namespace of Discord.Net.

## Subagents

- Claude Code may spawn subagents without asking first: for broad code searches, research, and parallel work on independent parts of a change.
- **Review before every PR:** once a change builds, a subagent reviews the diff against `release` for bugs, thread-safety, the rules above (token, mentions, presence, never blocking the game thread or the gateway) and leftovers. Fix what it confirms, then open the PR.
- Subagent findings are input, not orders: verify each against the code before acting on it.

## First build — things written without a compiler

This code was written against Dalamud API 15 documentation without compiling. Likely spots to fix on the first `dotnet build`:

1. `IChatGui.ChatMessage` handler signature: expects `OnHandleableChatMessageDelegate(IHandleableChatMessage message)` with `message.LogKind`, `message.Sender`, `message.Message` (API 15 replaced the old `(XivChatType, int, ref SeString, ref SeString, ref bool)` form).
2. `IClientState.Login` (`Action`) and `IClientState.Logout` (`Action<int, int>`) event signatures.
3. `IPlayerState.HomeWorld.ValueNullable?.Name.ExtractText()` — Lumina `RowRef<World>` / `ReadOnlySeString` API.
4. `Dalamud.Bindings.ImGui` overloads in `ConfigWindow`: `InputText(label, ref string, int maxLength, ImGuiInputTextFlags)`, `InputInt(label, ref int, step, stepFast)`.
5. `IPluginLog.Error(Exception?, string, params object[])` overload resolution when the exception may be null.
6. Discord.Net: `SocketGuild.SearchUsersAsync(string, int, RequestOptions)`, `RestGuildUser.DisplayName/GlobalName/Nickname`, `SocketRole.IsMentionable`, `AllowedMentions.None`, `AllowedMentions.UserIds/RoleIds` setters, `Discord.Net.WebSocketClosedException.CloseCode/Reason`, `RequestOptions.CancelToken`.
7. `IDalamudPluginInterface.UiBuilder` is typed `IUiBuilder`, whose icon font property is `FontIcon` (the concrete `UiBuilder` also has `IconFont`). `ImGui.SeparatorText` and `ImGui.SetItemTooltip` do not exist in `Dalamud.Bindings.ImGui`; use `ImRaii` (`Dalamud.Interface.Utility.Raii`) for scoped Begin/End pairs.
8. Collection expressions (`[]`) and `record struct` need C# 12+; the SDK sets LangVersion 14.

If a duplicate `Newtonsoft.Json` reference warning appears (Dalamud ships 13.0.4, Discord.Net wants ≥13.0.4), it is harmless; only set `<Use_Dalamud_Newtonsoft_Json>false</Use_Dalamud_Newtonsoft_Json>` if it turns into an error.
